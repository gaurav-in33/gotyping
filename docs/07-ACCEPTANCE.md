Hindi). *(DOM suite drives real `KeyboardEvent`s, a `beforeinput` soft-keyboard event, and on-screen-keyboard taps for both English and Hindi InScript; USB/OTG keyboards fire the same `KeyboardEvent`s as any other physical keyboard, so there is nothing further to special-case or test. **Real bug found and fixed this follow-up session:** `OnScreenKeyboard.tsx` only ever emitted a key's un-shifted glyph on tap, even when the expected/highlighted character required Shift (e.g. several Hindi InScript matras live only on the Shift layer) — tapping the correctly-highlighted key typed the wrong character and the test could never advance. ## Non-functional
- [x] No ads, no analytics, no third-party requests (verify in the network panel: same-origin only). No sound code or sound UI. *(Directly grepped the whole `src/` tree for `fetch`/`XMLHttpRequest`/`sendBeacon`/`WebSocket` — zero matches — and for any `http(s)://` reference in `src/`, `public/` and `index.html` — the only hit is the non-fetched SVG namespace string in `favicon.svg`. No audio code exists anywhere in the project.)*
- [x] No mandatory sign-in. Works offline for core features. *(No authentication code exists anywhere in the app — it is local-storage/IndexedDB only by design; offline support verified per the PWA item above.)*
- [x] No storage writes during a test. *(Read `TypeScreen.tsx`'s completion handler directly: `historyRepo.add` / `idb.put` only run once, from the `complete`/`fail` event handler after a test ends — the per-keystroke `feed`/`back` path never touches `idb` or `localStorage`.)*
- [ ] Typing latency: no dropped frames on a mid-range phone; no layout reads in the keystroke path. **Partially verified:** read `TextRenderer.ts` directly — `measure()` is the only place that reads `offsetLeft`/`offsetTop`/`offsetWidth`/`offsetHeight`, and it is documented and called only "after a text change, on resize and on font/width changes" — the per-keystroke `update()` path only touches cached arrays, no live DOM reads. The "no dropped frames on a mid-range phone" half cannot be measured without real hardware, so the item stays unchecked overall.
- [ ] Lighthouse Performance ≥ 95 and Accessibility ≥ 95 (mobile profile); report the numbers. **Not obtainable in this sandbox.** No Chromium could be installed (`apt-get` has no route to its package mirror; Puppeteer's and Playwright's own Chrome downloads both fail on TLS). No Lighthouse numbers are available — this is a sandbox limitation, not a claim about the real numbers either way.
- [x] `npm run build` and `npm test` pass; no TypeScript errors; no console errors. *(Verified repeatedly this session: clean `npm run build`, `npx tsc --noEmit` with zero errors, and 284/284 tests passing across 16 files; several DOM tests explicitly assert `console.error` was never called while rendering Learn/Practice/Stats/Tools/fun-mode switches.)*
- [x] No dead buttons, no placeholder screens, no duplicate features; loading/empty/error states exist. *(Full audit done this follow-up session: every `onClick` handler across `src/features/**/*.tsx` and `src/ui/**/*.tsx` was read and confirmed to do something real (not empty, not console-log-only), and every `<button>` was checked for a handler at all. **Two no-op buttons found and fixed:** (1) `ThemeBuilder.tsx`'s live preview had an "Accent" swatch rendered as a focusable, clickable `<button>` with no `onClick` at all — clicking it did nothing. Fixed by making it `disabled`, `aria-hidden`, `tabIndex={-1}` (it is a pure color-preview, not a real control, so it should not present as one). (2) The shared `KeyboardDiagram` component (`src/ui/components/KeyboardDiagram.tsx`) always rendered every key as a `<button>`, but two of its three callers — Stats → Keys heatmap and Tools → Keyboard tester — never pass an `onKeyClick`, so every key on those two screens was a focusable, clickable control that did nothing on click. Fixed by rendering a non-interactive `<span>` instead of `<button>` when no `onKeyClick` is supplied; the on-screen typing keyboard (`OnScreenKeyboard.tsx`, the only caller that does pass a handler) is unaffected and still a real button. Also found during the earlier Step 3 follow-up pass but recorded here for completeness: the on-screen keyboard's Shift-tap bug (see below) was a *correctness* bug rather than a no-op, and is listed separately. The section registry pattern (only built sections appear in navigation) continues to prevent dead nav links by construction, and the DOM suite confirms screens render with no console errors with real empty states on Stats/Practice.)*
